# 代码库理解机制

## 代码文件截断的特殊问题

代码文件和日志文件有本质区别：

```
日志文件（可能前重后轻）：
[1-2000行] 主要日志内容
[2001-3000行] 新增日志（可能是重复的或不重要的）

代码文件（可能前轻后重）：
[1-500行]    import 语句
[501-1000行]  注释和辅助函数
[1001-2000行] 主要类定义的前半部分
[2001-3000行] 主要类定义的后半部分 ← 核心逻辑可能在这里！
```

**如果截断发生在代码文件的关键位置，后果很严重：**

```
假设一个 3000 行的类定义文件被截断为 2000 行：

class ShoppingCart {
  // 前 2000 行：属性、getter/setter、简单方法
  private items: CartItem[] = [];

  addItem(item: CartItem) { ... }    // 前 2000 行
  removeItem(id: string) { ... }  // 前 2000 行

  // 截断！
  // ↓
  // 后 1000 行（被截断）：

  checkout() {           // ← 核心方法！
    // 支付流程、库存检查、
    // 优惠券处理等复杂逻辑
  }

  calculateTotal() {      // ← 核心方法！
    // 复杂的计费逻辑
  }
}
```

大模型只能看到前 2000 行，**完全不知道有 checkout 和 calculateTotal 这两个核心方法**！

## OpenCode 的代码库理解策略

### 关键认知：不是靠"截断后智能恢复"，而是靠"分段读取积累"

OpenCode 的策略不是"截断后智能恢复"，而是**通过多次分段读取，最终累积成完整的文件理解**。

### Read 工具的分段读取机制

```typescript
// src/tool/read.ts:21-22
parameters: z.object({
  filePath: z.string(),
  offset: z.coerce.number().describe("The line number to start reading from (0-based)").optional(),
  limit: z.coerce.number().describe("The number of lines to read (defaults to 2000)").optional(),
})
```

**默认只读 2000 行，但支持分段读取。**

### 实际的代码库理解流程

```
用户问题："解释 ShoppingCart 类的实现"

↓ 大模型不会直接 Read 整个文件！

而是先用 Glob 找到文件：
Glob({ pattern: "**/*cart*.ts" })
→ ["src/cart/Cart.ts", "src/cart/Item.ts", ...]

↓ 使用 Grep 搜索类定义：
Grep({ pattern: "class.*Cart", path: "src" })
→ 找到 class ShoppingCart 在 src/cart/Cart.ts

↓ 先读取文件的"开头"部分（看看结构）：
Read({ filePath: "src/cart/Cart.ts", limit: 50 })
→ 看到类名、导入语句、属性定义

↓ 使用 Grep 搜索方法定义：
Grep({ pattern: "  [a-zA-Z_]+\\(", path: "src/cart/Cart.ts" })
→ 找到所有方法名：addItem, removeItem, checkout, calculateTotal

↓ 逐个读取方法的实现：
Read({ filePath: "src/cart/Cart.ts", offset: 500, limit: 100 })  // 读取 addItem
Read({ filePath: "src/cart/Cart.ts", offset: 800, limit: 200 })  // 读取 checkout
Read({ filePath: "src/cart/Cart.ts", offset: 1200, limit: 150 }) // 读取 calculateTotal
```

**关键：每次只读一小段，通过多次调用最终理解完整文件，不会因为单次调用截断而丢失信息。**

## 为什么这样设计能避免截断问题？

### 1. 避免单次读取触发截断

```typescript
// src/tool/truncation.ts - 截断机制
export function truncation(content: string, limit: number): string {
  // 如果内容超过限制，会被截断
  if (content.length > limit) {
    return content.substring(0, limit) + "\n\n[Output was truncated]"
  }
  return content
}
```

```
错误做法（会触发截断）：
Read({ filePath: "large-file.ts" })
→ 假设文件有 10000 行
→ 全部读取会触发 Truncate（src/tool/truncation.ts）
→ 只能看到前 2000 行

正确做法（避免截断）：
Read({ filePath: "large-file.ts", limit: 50 })
→ 只读前 50 行，了解文件结构
→ 然后根据需要分段读取
→ 每次读取的量都在控制范围内
→ 通过多次调用最终理解完整文件
```

### 2. 使用搜索定位，而不是盲目读取

```typescript
// src/tool/glob.ts:9-19 - Glob 工具定义
export const GlobTool = Tool.define("glob", {
  parameters: z.object({
    pattern: z.string().describe("The glob pattern to match files against"),
    path: z.string().optional().describe("The directory to search in"),
  }),
  // 返回匹配的文件列表（按修改时间排序）
})

// src/tool/grep.ts:12-18 - Grep 工具定义
export const GrepTool = Tool.define("grep", {
  parameters: z.object({
    pattern: z.string().describe("The regex pattern to search for"),
    path: z.string().optional().describe("The directory to search in"),
  }),
  // 返回匹配的行号和内容（最多 100 条结果）
})
```

```
错误做法：
Read({ filePath: "Cart.ts" })
→ 读整个文件可能触发截断

正确做法：
Grep({ pattern: "checkout", path: "Cart.ts" })
→ 找到 checkout 方法的位置（比如第 800 行）
Read({ filePath: "Cart.ts", offset: 795, limit: 50 })
→ 只读取 checkout 方法及其附近的内容
→ 多次这样的调用可以覆盖整个文件
```

### 3. 子会话隔离

```
主会话的 Token 预算：
- 当前对话历史：100,000 tokens
- 可用空间：100,000 tokens

如果在主会话中处理大文件：
- 读取 5000 行代码：50,000 tokens
- 总共：150,000 tokens → 可能溢出

使用子会话：
- 子会话独立计算 Token
- 即使子会话用了 50,000 tokens
- 主会话只收到汇总结果：500 tokens
```

```

第 1 步：定位文件
  Grep({ pattern: "class OrderProcessor" })
  → 找到文件：src/order/OrderProcessor.ts

第 2 步：初步了解文件结构
  Read({ filePath: "src/order/OrderProcessor.ts", limit: 100 })

  2  import { OrderService } from './order.service'
   3  import { PaymentService } from './payment.service'

        ↓

```

**与一次性读取的区别：**

```
一次性读取（错误）：
Read({ filePath: "5000行文件.ts" })
→ 触发截断机制（src/tool/truncation.ts）
→ 只返回前 2000 行
→ 大模型看不到后 3000 行

分段读取（正确）：
Read({ offset: 0, limit: 1000 })
Read({ offset: 1000, limit: 1000 })
Read({ offset: 2000, limit: 1000 })
Read({ offset: 3000, limit: 1000 })
Read({ offset: 4000, limit: 1000 })
→ 每次都不触发截断（因为单次读取量小）
→ 大模型最终看到完整的 5000 行
```

**所以准确的理解是：**

- 不是"从未读取完整文件"
- 而是"通过多次分段调用，最终读取了完整文件"
- 关键优势：每次调用都在 Token 限制内，不会因为截断而丢失信息
```

## 总结：代码库理解的三层机制

### 第一层：文件定位（Glob + Grep）
```
不读取内容，只找文件位置和关键行号
- Glob：按模式找文件
- Grep：按模式找内容位置
```

### 第二层：结构采样（Read + offset/limit）
```typescript
// src/tool/read.ts:56-64 - Read 工具定义
export const ReadTool = Tool.define("read", {
  parameters: z.object({
    filePath: z.string(),
    offset: z.coerce.number().describe("The line number to start reading from (0-based)").optional(),
    limit: z.coerce.number().describe("The number of lines to read (defaults to 2000)").optional(),
  }),
  // 返回指定范围的内容
})
```
```
通过分段读取避免单次截断，最终累积成完整理解
- Read({ limit: 50 })：读文件头部，了解结构
- Read({ offset: X, limit: Y })：读特定范围
- 多次调用的结果都会返回给大模型，累积在对话历史中
- 每次调用都不触发截断（因为单次读取量可控）
```

### 第三层：子代理隔离（Task + 独立会话）
```
对于复杂分析，创建独立子会话
- 子会话可以多次调用工具
- 不影响主会话的 Token 预算
- 最终只返回汇总结果
```

**关键理解：OpenCode 不是靠"截断后智能恢复"来解决代码理解问题，而是通过"分段读取 + 多次累积"的方式，让大模型最终理解完整的代码文件，同时避免单次调用触发截断导致信息丢失。**
